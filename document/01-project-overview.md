# 스마트 중고차 수출 ERP 시스템 프로젝트 개요

## 1. 과제 정보

- 과제명: 풀링포레스트 2차 과제
- 과제 링크: [풀링포레스트 채용 과제 안내](https://www.pooolingforest.com/careers/challenge)
- 프로젝트명: 스마트 중고차 수출 ERP 시스템
- 패키지명: `cartrace` (npm·Vercel 프로젝트 식별자)
- 프로젝트 형태: 중고차 수출 운영 ERP 가안
- 구현 목적: 회계팀과 영업팀의 업무 리스크를 화면과 흐름으로 빠르게 검증하는 것

## 2. 프로젝트 소개

스마트 중고차 수출 ERP 시스템은 중고차 수출 업무에서 차량별 매입·선적·증빙·환율·권리 조회 상태를 추적하고, 회계팀이 확인해야 할 리스크와 미결 업무를 빠르게 발견하도록 돕는 운영 ERP 가안이다. 구현 패키지명은 `cartrace`로 유지한다.

차량 한 대를 하나의 업무 레코드로 관리하며, 계약·지급·권리 조회·수출·증빙·정산 상태를 하나의 흐름으로 연결한다. 사용자는 “이 차량이 지금 어디까지 처리됐는가”, “무엇이 부족한가”, “다음에 누가 무엇을 해야 하는가”를 화면에서 바로 확인할 수 있다.

## 3. 프로젝트 배경

중고차 수출 업무는 영업팀의 거래 속도와 회계팀의 증빙·세무·정산 통제가 동시에 필요하다. 그러나 차량 정보, 계약서, 인보이스, 수출신고필증, B/L, 외화 입금증명, 권리 조회 결과가 여러 문서와 엑셀에 흩어지면 거래가 진행될수록 다음 문제가 커진다.

- 차량이 현재 매입·선적·증빙 중 어느 단계인지 바로 알기 어렵다.
- 필요한 증빙이 무엇이고 누가 언제까지 처리해야 하는지 놓치기 쉽다.
- 계약 금액, 입금액, 인보이스 금액, 수출신고 금액 사이의 불일치를 늦게 발견할 수 있다.
- 선적 전 권리 문제나 선적 후 증빙 누락이 다음 거래의 리스크로 이어질 수 있다.
- 회계팀은 사후에 자료를 모아 확인하고, 영업팀은 업무가 막히는 이유를 늦게 알게 된다.

## 4. 프로젝트 목적

이번 과제의 목적은 완성된 ERP를 개발하는 것이 아니다. 회계팀 또는 회계팀장에게 다음 질문에 답하는 초기 화면과 업무 흐름을 빠르게 보여주는 것이다.

1. 이 차량은 지금 어디까지 처리됐는가?
2. 무엇이 아직 부족하고, 누가 처리해야 하는가?
3. 지금 막아야 하는 거래인가, 미결로 남기고 다음 단계로 진행할 수 있는가?
4. 금액·환율·증빙의 불일치를 어떻게 발견하고 통제하는가?
5. 사람이 임의로 상태를 바꾼 것이 아니라 누가 언제 확인했는가?

## 5. 해결하려는 핵심 문제

### 5.1 상태가 흩어져 업무 위치를 알기 어려운 문제

차량 정보, 매입 계약, 수출 계약, 선적 정보, 증빙 문서가 서로 다른 곳에 있으면 “이 차가 지금 어디까지 됐는지” 확인하는 데 시간이 걸린다.

**해결 방향:** 차량 하나를 기준으로 업무 상태와 관련 데이터를 연결하고, 목록·상세·미결 화면에서 같은 기준으로 보여준다.

### 5.2 증빙 누락을 사후에 발견하는 문제

수출신고필증, B/L, 외화 입금증명 등 필요한 증빙이 거래 유형과 단계에 따라 달라지는데, 누락을 거래 종료 직전에 발견하면 회계팀의 재작업과 환급 지연으로 이어진다.

**해결 방향:** 거래 유형별 필수 증빙을 체크리스트로 계산하고, 담당자·기한·미처리 사유를 미결 알림으로 남긴다.

### 5.3 금액과 환율 불일치를 사람이 눈으로 찾는 문제

계약 금액, 실제 입금액, 인보이스 외화 금액, 적용 환율, 수출신고 원화 금액이 서로 다를 수 있다. 정상적인 환율 차이와 실제 오류를 구분하지 못하면 불필요한 경고가 생기거나 중요한 오류를 놓칠 수 있다.

**해결 방향:** 외화 금액·적용 환율·환산 원화 금액을 분리 저장하고, 비교 기준과 허용 범위를 명시한 뒤 불일치 유형별로 알린다.

### 5.4 모든 누락을 같은 방식으로 막는 문제

권리 이상처럼 되돌릴 수 없는 손해와, 서류 지연처럼 이후 회수할 수 있는 손해를 모두 같은 하드 블록으로 처리하면 영업 속도가 지나치게 떨어진다.

**해결 방향:** 되돌릴 수 없는 위험은 하드 게이트로 차단하고, 회수 가능한 손해는 미결·기한·에스컬레이션으로 관리한다.

### 5.5 상태 변경의 책임이 남지 않는 문제

사람이 매출 인식일이나 증빙 상태를 임의로 바꾸면 사후 감사에서 “현재 상태”만으로는 판단 근거를 확인할 수 없다.

**해결 방향:** 상태 변경에는 변경자·변경 시각·변경 사유·이전 값·변경 값을 함께 기록한다.

## 6. 핵심 원칙

> 되돌릴 수 없는 손해는 막고, 돈으로 메울 수 있는 손해는 빚으로 남겨 다음 거래에서 회수한다.

## 7. 포함 범위

- 회계팀과 영업팀의 업무 흐름을 설명하는 운영 화면
- 차량 단위 상태와 증빙 체크리스트
- 미결·알림 규칙과 하드 게이트
- 금액·환율·증빙 불일치 표시
- 담당자·기한·에스컬레이션 정보
- 상태 변경 감사 이력
- Mock JSON 기반의 빠른 가안
- Vercel Preview 배포를 위한 정적 빌드

## 8. 제외 범위

- 실제 외부 API 연동
- 실제 데이터베이스 구축
- 실제 세무 신고·수출 신고 처리
- 실제 결제·환율·문서 저장 연동
- 완성된 권한 관리와 운영자 관리
- 모든 예외 케이스에 대한 법률·세무 자동 판단

## 9. 전체 성공 기준

초기 가안은 다음 질문에 화면만 보고 답할 수 있으면 성공으로 본다.

- 어떤 차량이 지금 막혀 있는가?
- 왜 막혀 있는가?
- 누가 언제까지 처리해야 하는가?
- 지금 반드시 막아야 하는 거래인가?
- 미결로 진행했다면 다음 거래에서 어떻게 회수할 것인가?
- 이 상태와 판단을 누가 언제 확인했는가?

세부적인 단계별 성공 기준과 검증 규칙은 [업무 흐름 및 검증 로직](./02-workflow-and-validation.md)에 정리한다.

구체적인 기능 정의와 화면 구성은 [핵심 기능 및 화면 범위](./04-features-and-screens.md)에 정리한다.
