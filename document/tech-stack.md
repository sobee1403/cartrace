# CarTrace 기술 스택 및 초기 개발 방향

## 1. 프로젝트 목적

CarTrace는 중고차 수출 업무에서 차량별 매입·선적·증빙·환율·권리 조회 상태를 한 화면에서 추적하고, 회계팀이 확인해야 할 리스크를 빠르게 발견하도록 돕는 운영 ERP 가안이다.

이번 과제의 핵심은 완성된 백오피스 시스템을 만드는 것이 아니라, 회계팀과 영업팀의 업무 충돌을 어떤 화면과 규칙으로 줄일 수 있는지 빠르게 보여주는 것이다.

## 2. 초기 기술 스택

| 영역 | 선택 | 선택 이유 |
| --- | --- | --- |
| Frontend build tool | Vite | 정적 가안 화면을 빠르게 개발하고 `dist/`로 빌드한다. |
| UI library | React | 컴포넌트 단위로 운영 화면을 빠르게 조합한다. |
| Language | TypeScript | 차량·증빙·알림·상태 전이처럼 필드가 많은 도메인 모델의 오류를 줄인다. |
| Styling | Tailwind CSS | 가안 화면을 빠르게 조정하고 반응형 레이아웃을 만들기 쉽다. |
| Quality | ESLint | 제출 전 기본적인 코드 품질과 실수를 확인한다. |
| Deployment | Vercel | Vite가 만든 `dist/` 결과물을 빠르게 Preview와 배포 URL로 제공한다. |
| Data | 초기에는 Mock JSON/TypeScript 상수 | 백엔드 API나 DB 구축보다 업무 흐름과 UI 설득력을 먼저 검증한다. |

## 3. 왜 Vite + React인가

이번 과제는 회계팀 또는 회계팀장에게 “이 기능이 실제 업무를 어떻게 통제하고, 어떤 리스크를 줄이는가”를 초기 화면으로 어필하는 것이 목적이다. 따라서 처음부터 복잡한 백엔드와 데이터베이스를 만들기보다, 실제 업무 흐름을 반영한 가안을 빠르게 개발하고 빌드하여 Vercel URL로 보여주는 편이 효과적이라고 판단했다.

이번에는 확장성보다 **빠른 가안 제작과 발표 준비**를 우선하므로 Vite + React를 선택한다.

Vite는 Vercel 같은 호스팅 서비스가 아니라, React 화면을 개발하고 production build를 만드는 프론트엔드 도구다. Vercel은 Vite가 생성한 `dist/` 폴더를 호스팅하고 Preview URL을 제공하는 배포 서비스다.

선택 이유는 다음과 같다.

1. **개발 서버와 HMR이 빠르다.** 화면을 만들고 수정한 결과를 바로 확인할 수 있다.
2. **정적 가안에 필요한 구조만 유지한다.** Next.js의 서버 기능이나 라우팅 구조를 지금 단계에서 추가하지 않는다.
3. **Vercel에 바로 배포할 수 있다.** `vite build`로 생성한 `dist/`를 Vercel이 자동 감지해 배포할 수 있다.
4. **React와 TypeScript를 그대로 사용한다.** 화면이 늘어나도 컴포넌트와 도메인 타입을 재사용할 수 있다.

Vercel은 Next.js뿐 아니라 React/Vite, Vue/Nuxt, SvelteKit, Astro, Angular 및 정적 사이트도 배포할 수 있다. 따라서 이번 프로젝트에서는 Vercel과 Vite를 서로 다른 역할로 이해한다.

## 4. 다른 선택지와 비교

### Next.js

Next.js는 라우팅, 서버 렌더링, API, 인증 등 확장 기능을 한 프로젝트 안에서 다루기 좋다. 다만 이번 과제에서는 아직 그 기능이 필요하지 않고, 초기 방향과 화면 설득력을 빠르게 보여주는 것이 우선이므로 사용하지 않는다.

### Vite + React

현재 과제처럼 Mock Data 기반의 정적 가안과 빠른 Vercel Preview가 목적이라면 Vite + React가 더 단순하고 효율적이다. 이후 서버 기능이 필요해지는 시점에 별도로 판단한다.

### 단순 HTML/CSS/JavaScript

가장 빠르게 한 화면을 만들 수 있지만, 화면 간 상태와 타입을 관리하기 어렵고 이후 컴포넌트 재사용이나 배포 구조 확장이 불편하다. 이번 과제의 화면 수와 도메인 데이터 구조를 고려하면 장기적으로 비효율적이다.

### Retool·저코드 도구

관리자 화면을 빠르게 만들 수 있지만, 과제에서 보여주려는 업무 로직과 UI 설계 의도를 세밀하게 표현하기 어렵고 제출물의 코드 확장성도 제한될 수 있다.

## 5. 초기 구현 범위

### 우선 구현할 화면

- **차량 목록:** 현재 재고, 매입 진행, 선적 대기, 미증빙, 24시간 초과 미결 KPI
- **차량 상세:** 차량 기본 정보, 권리 조회, 증빙 체크리스트, 금액·환율 불일치, 상태 이력
- **미결·알림:** 무엇이, 어느 차량에서, 왜 발생했고, 누가 언제까지 처리해야 하는지 표시

### 초기 데이터 전략

실제 외부 API와 DB는 연결하지 않고 JSON Mock Data로 구현한다. 대신 다음 데이터 구조는 실제 도메인을 고려해 설계한다.

- 차량 및 VIN
- 매입 계약과 지급 상태
- 수출 계약·인보이스·환율
- 권리 조회 결과
- 증빙 문서와 제출 기한
- 미결 알림과 에스컬레이션 이력

## 6. 배포 및 검증 기준

```bash
npm run lint
npm run build
npm run dev
```

초기 목표는 다음과 같다.

- 로컬에서 기본 화면이 정상 실행될 것
- `lint`와 `build`가 통과할 것
- Vercel Preview URL에서 동일한 화면이 열릴 것
- 회계팀이 “무엇이 막혔고, 왜 막혔으며, 다음에 무엇을 해야 하는지”를 빠르게 이해할 수 있을 것

## 7. 한 줄 의사결정

**회계팀에게 업무 통제 로직이 실제로 작동하는 가안을 빠르게 보여주기 위해, Vite + React로 화면을 만들고 Vercel로 빠르게 배포한다.**
