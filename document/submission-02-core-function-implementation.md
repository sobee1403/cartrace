# 02. 핵심 기능 구현

## 과제 요구사항 반영

이 구현은 대시보드를 만들지 않는다. 매입·매출이 일어나는 순간의 업무 흐름과 각 단계의 리스크 통제 방식을 프론트엔드로 보여주는 데 집중한다.

- 복잡한 백엔드 로직은 구현하지 않는다.
- 실제 환율·압류 조회 API는 연동하지 않는다.
- 실제 DB는 구축하지 않는다.
- JSON과 TypeScript Mock Data를 사용한다.
- 핵심 통제 로직은 화면의 상태·검증 카드·미결 알림으로 표현한다.

구현 범위는 [프로젝트 개요](./01-project-overview.md), [업무 흐름 및 검증 로직](./02-workflow-and-validation.md), [핵심 기능 및 화면 범위](./04-features-and-screens.md)를 기준으로 한다. 구현 후 화면에서 확인한 내용을 바탕으로 [솔루션 기획안](./submission-01-solution-plan.md)을 최종 다듬는다.

## 평가 기준을 만족하기 위한 필수 구현

- **매입·매출 언밸런스 체크:** 계약·지급·인보이스·환율·수출신고 데이터를 비교한다.
- **VIN 검증:** 중복 VIN, 권리 이상, 매입 전·선적 전 조회 결과를 보여준다.
- **엑셀 대체 UX:** 차량별 업무 단계, 증빙, 담당자, 기한, 최근 변경을 한 화면에서 확인한다.
- **안심 알람:** 알림마다 담당 팀·원인·담당자·기한·미처리 시 영향·잠금 여부를 표시한다.

### 구현 범위 원칙

평가 대상은 완성된 ERP 전체가 아니라, 매입·매출 순간의 리스크 통제 UX다. 따라서 실제 동작은 핵심 시나리오에 집중한다.

- 외부 API·DB 대신 고정된 Mock Data로 검증 시나리오를 재현한다.
- 상세 상태 8단계는 내부 로직과 이력에 사용하되, 화면에서는 `매입`, `재고`, `수출 준비`, `선적`, `증빙`의 5개 매크로 단계로 단순화한다. 수출 준비와 실제 선적 직전 통제를 분리해 선적 하드 게이트를 명확히 보여준다.
- 감사 이력은 실제 감사 로그 시스템이 아니라 차량 상세의 정적 타임라인으로 구현한다.
- 에스컬레이션은 실제 메일·메신저 발송이 아니라 알림 상태와 담당자 표시로 구현한다.
- 부가세는 세액을 자동 계산하지 않고, 증빙 누락·환급 지연·과세 리스크를 알림으로 보여준다.

## 1. 구현 목표

사용자가 차량 한 대를 선택했을 때 다음을 바로 이해할 수 있어야 한다.

1. 현재 업무 단계는 어디인가?
2. 다음에 해야 할 액션은 무엇인가?
3. 어떤 리스크가 발견됐는가?
4. 지금 거래를 막아야 하는가?
5. 미결로 진행한다면 담당자와 기한은 누구에게 배정됐는가?

## 2. 구현 화면

### 화면 A. 차량 목록

차량별 상태·위험·미결을 확인하고 차량 상세로 진입하는 화면이다.

구현 항목:

- 전체 차량 목록
- 상태 필터
- 위험 플래그
- 누락 증빙 수
- 담당자
- 최근 변경 시각
- 하드 게이트 여부
- 미결 기한 초과 여부

이 화면은 엑셀의 여러 시트를 오가며 확인하던 정보를 차량 단위로 합쳐, 회계팀장이 “어떤 차량부터 봐야 하는가”를 바로 판단하게 한다.

### 화면 B. 차량 상세

실제 업무가 발생하는 순간의 검증과 통제를 보여주는 핵심 화면이다.

구현 항목:

- 차량 기본 정보와 VIN
- 현재 상태와 다음 액션 버튼
- 권리 조회 결과
- 거래 유형별 증빙 체크리스트
- 계약 금액과 지급액 비교
- 인보이스·환율·수출신고 금액 비교
- 미결 알림과 담당자
- 상태 변경 이력

버튼이 비활성화된 경우 버튼 옆에 차단 이유와 해제 조건을 표시한다.

이 화면은 매입·매출이 발생하는 순간의 언밸런스 체크와 VIN 검증을 한 곳에서 보여주는 핵심 화면이다.

증빙 체크리스트는 전체 문서를 한 묶음으로 보여주지 않고, 업무 시점별로 나눈다.

- **매입 확정 전:** 매입 계약서, 소유권 확인 자료, 지급 증빙
- **선적 전:** 수출신고필증 및 선적을 허용하기 위한 필수 서류
- **선적 후:** B/L, 외화 입금증명 등 사후 증빙

각 항목 옆에는 해당 문서의 보완 마감과 업로드 버튼을 둔다. 파일을 업로드하면 현재 화면에서만 `서류 구비 완료 · 검토 대기`로 바뀐다. 첨부는 단계 승인이나 자동 전이가 아니며, 별도의 `승인 요청` 이후 회계·영업 검토가 완료되어야 다음 단계로 이동한다. 실제 저장·파일 유효성 검증은 과제 범위에서 제외한다. 실제 서비스에서는 증빙 종류별 확장자·파일 내용·VIN·금액·날짜를 검증한 뒤 통과한 파일만 구비 완료 처리한다.

차량 상세의 증빙 체크리스트는 모든 차량에 같은 항목을 보여주지 않는다. 매입 타입과 지급 방식에 따라 필요한 증빙을 계산한다.

### 화면 C. 미결·알림

처리가 늦어지는 업무를 담당자와 기한 기준으로 처리하는 화면이다.

구현 항목:

- 24시간 초과 미결
- 오늘 처리 필요
- 팀장 확인 필요
- 차량·VIN
- 발생 이유
- 담당자
- 남은 기한
- 미처리 시 영향
- 담당 팀: 영업팀 확인 필요 또는 회계팀 확인 필요
- 관련 차량 상세로 이동

알림은 `어느 팀이 먼저 확인해야 하는지`, `무엇이 문제인지`, `누가 언제까지 처리해야 하며`, `처리하지 않으면 어떤 거래가 잠기는지`까지 보여준다. 개인 담당자는 팀 라우팅 아래에 보조 정보로 표시해 동선 착오를 줄인다.

## 3. Mock Data 구조

```ts
type VehicleStatus =
  | "purchase"
  | "inventory"
  | "export"
  | "evidence";

type Vehicle = {
  id: string;
  vin: string;
  model: string;
  year: number;
  purchaseType: "dealer" | "individual" | "auction";
  saleType: "export";
  status: VehicleStatus;
  riskFlags: string[];
  assignee: string;
};

type ValidationAlert = {
  id: string;
  vehicleId: string;
  type: "missing_evidence" | "amount_mismatch" | "rights_detected" | "duplicate_vin";
  reason: string;
  owner: string;
  dueAt: string;
  impact: string;
  severity: "info" | "warning" | "blocking";
};
```

## 4. 매입 타입별 증빙 규칙

매입 타입에 따라 거래 상대방과 거래 증빙의 구조가 다르므로, 하나의 고정 체크리스트를 사용하면 회계팀에게는 불필요한 경고가 생기고 영업팀에게는 실제로 필요한 증빙이 가려진다.

아래 표는 과제 가안에서 사용할 증빙 규칙이다. 실제 세무·법무 기준을 확정하는 표가 아니라, 화면에서 매입 유형별 요구사항이 다르게 계산되는 것을 보여주기 위한 제품 규칙이다.

| 매입 타입 | 기본 증빙 | 거래 방식에 따른 추가 증빙 | 주요 검증 | 다음 단계 통제 |
| --- | --- | --- | --- | --- |
| 딜러 매입 | 매입 계약서, 차량등록 관련 서류, 사업자 정보, 지급 증빙 | 계산서·세금계산서 또는 거래명세서, 계좌이체 내역 | 계약 상대방과 사업자 정보 일치, 계약 금액과 지급액 일치, 계산서 금액 확인 | 지급·기본 증빙이 없으면 매입 확정 보류 |
| 개인 매입 | 매매 계약서, 차량등록 관련 서류, 판매자 신원·소유권 확인, 지급 증빙 | 개인 거래 확인 자료, 계좌이체 내역 또는 현금 지급 확인 | 판매자와 등록 소유자 일치, 계약 금액과 지급액 일치, 소유권 이전 가능 여부 | 소유권 미확보 또는 지급 증빙 누락 시 매입 확정 보류 |
| 경매 매입 | 경매 낙찰 확인서, 경매 거래 명세, 차량등록 관련 서류, 낙찰·지급 증빙 | 경매 수수료 명세, 낙찰가와 실제 지급액 자료 | 낙찰 차량 VIN 일치, 낙찰가·수수료·지급액 구분, 권리 상태 확인 | VIN 불일치 또는 낙찰·지급 정보 누락 시 재고 편입 보류 |

### 지급 방식별 보완 규칙

매입 타입만으로 증빙이 모두 결정되지 않고, 실제 지급 방식에 따라 추가 증빙을 계산한다.

| 지급 방식 | 추가 확인 항목 | 불일치 시 처리 |
| --- | --- | --- |
| 계좌이체 | 이체일, 송금인, 수취인, 이체 금액 | 계약 금액과 다르면 금액 불일치 알림 생성 |
| 현금 | 현금 지급 확인 자료, 수령 확인자, 지급일 | 회계팀 검토 미완료 시 매입 확정 보류 |
| 계산서·세금계산서 | 발행 주체, 공급가액, 세액, 발행일 | 거래 상대방·계약 금액과 비교 후 검토 요청 |
| 경매 결제 | 낙찰가, 수수료, 결제 금액, 경매 거래번호 | 낙찰 정보와 VIN·지급액 불일치 시 재고 편입 보류 |

### 화면 동작

1. 사용자가 매입 타입을 선택한다.
2. 시스템이 해당 타입의 기본 증빙과 지급 방식별 추가 증빙을 계산한다.
3. 차량 상세의 증빙 체크리스트에 `필수`, `조건부`, `해당 없음` 상태로 표시한다.
4. 필수 증빙이 없으면 매입 확정 버튼을 비활성화한다.
5. 조건부 증빙이 아직 생기지 않은 경우, 담당자·기한을 가진 미결로 전환할 수 있다.
6. 체크리스트 변경 이력에 누가 기준을 변경했는지 남긴다.

### 예시: 같은 금액이라도 다른 검증

- 딜러 매입 3,000만 원: 사업자 정보와 계산서·거래명세서 확인
- 개인 매입 3,000만 원: 판매자 신원과 소유권, 지급 확인 중심
- 경매 매입 3,000만 원: 낙찰 확인서, 경매 수수료, 낙찰가와 지급액 분리 확인

따라서 화면에는 단순히 `증빙 2개 누락`이라고 표시하지 않고, `개인 매입: 소유권 확인 자료 누락`처럼 매입 타입과 누락 사유를 함께 보여준다.

## 5. 구현할 검증 시나리오

### 시나리오 1. 권리 이상 차량

- VIN 조회 결과에 압류·저당·도난 플래그가 있다.
- 차량 상세 상단에 위험 상태를 표시한다.
- 선적 버튼을 비활성화한다.
- 버튼 옆에 `권리 이상 해소 후 선적 가능`을 표시한다.

### 시나리오 2. 금액 불일치

- 계약 금액과 실제 지급액이 다르다.
- 불일치 금액과 차이를 표시한다.
- 담당자 검토 알림을 생성한다.
- 매입 확정 단계를 보류한다.

### 시나리오 3. 환율 차이

- 인보이스는 USD, 수출신고는 KRW로 저장한다.
- 적용 환율과 기준일을 함께 표시한다.
- 환율 기준으로 설명 가능한 차이는 경고로 표시한다.
- 허용 범위를 넘는 차이는 회계 검토 알림으로 표시한다.

### 시나리오 4. 선적 후 증빙 누락

- 선적은 허용한다.
- B/L·외화 입금증명 미첨부를 미결로 생성한다.
- 담당자와 기한을 표시한다.
- 기한 초과 시 다음 수출 계약 잠금과 팀장 에스컬레이션을 표시한다.

### 시나리오 5. 중복 VIN

- 활성 재고에 이미 존재하는 VIN을 등록한다.
- 신규 등록을 차단한다.
- 기존 차량 레코드로 이동할 수 있게 한다.

### 시나리오 6. 매입 타입 변경

- 딜러 매입에서 개인 매입으로 타입을 변경한다.
- 증빙 체크리스트가 사업자·계산서 중심에서 신원·소유권 확인 중심으로 바뀐다.
- 이미 첨부된 문서 중 더 이상 해당하지 않는 문서는 삭제하지 않고 `기준 변경으로 미사용` 상태로 보존한다.
- 타입 변경 사유와 변경자를 감사 이력에 남긴다.

## 7. 구현 완료 기준

- 목록에서 위험 차량과 미결 차량을 식별할 수 있다.
- 엑셀 없이 차량별 현재 단계·누락 증빙·담당자·기한을 한 화면에서 확인할 수 있다.
- 상세 화면에서 현재 상태와 다음 액션을 알 수 있다.
- 위험 조건에 따라 버튼이 실제로 비활성화된다.
- 버튼이 막힌 이유가 화면에 표시된다.
- 계약 금액·지급액·인보이스·환율·수출신고 금액의 언밸런스를 확인할 수 있다.
- VIN 중복과 권리 조회 결과를 확인할 수 있다.
- 증빙 누락과 금액 불일치가 Mock Data로 재현된다.
- 선적 후 증빙은 미결로 표시되고 담당자와 기한이 보인다.
- 알림에 원인·담당자·기한·미처리 시 영향이 표시된다.
- 알림에 영업팀·회계팀 중 1차 확인 팀이 명확히 표시된다.
- 화면의 상태가 5개 매크로 단계로 이해된다.
- 딜러·개인·경매 매입을 선택하면 서로 다른 증빙 체크리스트가 표시된다.
- 계좌이체·현금·계산서·경매 결제 방식에 따라 추가 검증 항목이 달라진다.
- 매입 타입 변경 시 체크리스트와 감사 이력이 함께 변경된다.
- `npm run lint`가 통과한다.
- `npm run build`가 통과한다.
- Vercel Preview에서 화면을 확인할 수 있다.
